# README — `docker-compose.yml` Explained Line by Line

This document provides a detailed explanation of the Docker Compose configuration, with particular attention to the bridge between the container and the host’s X11-compatible display system.

The project was tested on Debian 13 with GNOME running under Wayland. In this environment, XWayland provides compatibility for the X11 connection used by the container.

---

**Line 1**

```yaml
services:
```

This is a root-level key in the Docker Compose format.

It introduces the list of containers, called **services**, that Compose will build, start, stop, and manage.

This project defines only one service.

---

**Line 2**

```yaml
  calculator:
```

This defines the service name, which can be chosen freely.

The name is used by Docker Compose when generating resource names. For example, the resulting container may be named:

```text
calculatrice-calculator-1
```

In this example:

* `calculatrice` comes from the project directory name.
* `calculator` is the service name.
* `1` is the instance number generated by Compose.

The exact generated name can vary if a different Compose project name is specified.

---

**Line 3**

```yaml
    build: .
```

This tells Docker Compose to build the image using the Dockerfile located in the current project directory, represented by `.`.

The same directory also becomes the Docker build context.

Instead of downloading a previously published application image from a registry such as Docker Hub, Compose builds the image locally from the project files.

This is broadly equivalent to running:

```bash
docker build .
```

However, Docker Compose also applies the additional configuration defined in `docker-compose.yml`.

---

**Line 4**

```yaml
    image: qt-calculator
```

This assigns the name `qt-calculator` to the image created by the build.

Without this line, Docker Compose would generate an automatic image name based on the project and service names, such as:

```text
calculatrice-calculator
```

The assigned image name can be displayed with:

```bash
docker images
```

## Lines 5–7 — Environment Variables

```yaml
    environment:
      - DISPLAY=${DISPLAY}
      - QT_X11_NO_MITSHM=1
```

The `environment` section defines environment variables that are passed to the container when it starts.

### `DISPLAY=${DISPLAY}`

```yaml
      - DISPLAY=${DISPLAY}
```

This is one of the key lines required for graphical output.

The `${DISPLAY}` expression retrieves the value of the `DISPLAY` environment variable from the host environment in which Docker Compose is executed.

Typical values include:

```text
:0
```

or:

```text
:1
```

Compose passes this value to the container as its own `DISPLAY` environment variable.

The variable tells Qt which X11 display to contact. Without it, the application would not know where to display its window.

On the tested Debian 13 GNOME system, the desktop session uses Wayland. The `DISPLAY` variable points to the XWayland compatibility server, which accepts the container’s X11 connection and displays the window within the Wayland desktop session.

The communication path is therefore:

```text
PySide6 container → X11 protocol → XWayland → GNOME/Wayland → screen
```

### `QT_X11_NO_MITSHM=1`

```yaml
      - QT_X11_NO_MITSHM=1
```

This variable tells Qt not to use the MIT-SHM extension for its X11 communication.

MIT-SHM allows X11 clients and the display server to exchange image data through shared memory. This can improve graphical performance when both processes share a compatible system environment.

Container isolation can sometimes make this shared-memory mechanism unsuitable or cause compatibility problems. Setting:

```text
QT_X11_NO_MITSHM=1
```

instructs Qt to use the regular X11 communication path instead.

For a small application such as this calculator, the possible performance difference is negligible, while disabling MIT-SHM can improve compatibility between the container and the host display system.

This setting does not disable X11. It disables only the MIT-SHM optimization used within X11 communication.

## Lines 8–9 — Volume Mount

```yaml
    volumes:
      - /tmp/.X11-unix:/tmp/.X11-unix:rw
```

The `volumes` section defines files or directories shared between the host and the container.

The syntax follows this structure:

```text
host_path:container_path:access_mode
```

In this project:

* The first `/tmp/.X11-unix` is the directory on the host.
* The second `/tmp/.X11-unix` is the location where it is mounted inside the container.
* `rw` specifies a read-write mount.

The host directory contains the Unix-domain sockets created by the X11 or XWayland display server.

For example, a display identified by:

```text
:0
```

generally corresponds to a socket named:

```text
/tmp/.X11-unix/X0
```

Mounting the directory at the same location inside the container gives the Qt application access to this socket.

Without this volume mount, the container could know the correct `DISPLAY` value but would have no local communication channel through which to reach the display server.

The two settings therefore have complementary purposes:

* `DISPLAY` identifies which display the application must contact.
* `/tmp/.X11-unix` provides the Unix socket used to establish that connection.

---

**Line 10**

```yaml
    network_mode: host
```

This setting makes the container use the host’s network stack instead of the isolated bridge network normally created by Docker.

As a consequence:

* The container does not receive its own isolated Docker network interface.
* The container shares the host’s network namespace.
* Services listening on network ports inside the container use the host’s network directly.
* Some of Docker’s normal network isolation is removed.

In the current project, the graphical connection primarily uses:

```text
DISPLAY + /tmp/.X11-unix
```

This means that the X11 connection is established through a mounted Unix-domain socket rather than through TCP.

For this particular local socket-based connection, `network_mode: host` is generally not required. It would become relevant only if the display server were contacted through a network address or TCP connection.

The option remains part of the project’s current configuration, but it is not one of the three essential elements that make the local X11 socket connection work.

---

## How the Display Connection Works

Running a graphical Qt application inside a container requires a controlled connection to the host’s display system.

In this project, three elements work together:

1. **`DISPLAY`** tells Qt which X11 or XWayland display it must contact.
2. **The `/tmp/.X11-unix` volume** gives the container access to the corresponding Unix socket.
3. **`xhost +local:docker`**, executed by the `calc` or `run.sh` script, changes the X server’s access-control list so that the required local connection is accepted.

The `xhost` command is not defined in `docker-compose.yml`. It must be executed on the host because it modifies the access permissions of the host’s X server.

An important detail is that:

```bash
xhost +local:docker
```

does not authenticate Docker as a uniquely identified application. With the `local` family, it grants access more broadly to local non-network connections accepted by the X server.

The matching command:

```bash
xhost -local:docker
```

removes this authorization after the calculator container has stopped.

For this reason, the authorization should remain active only while the application requires it, as implemented by the `calc` script.

## Relationship Between the Components

```text
Host DISPLAY value
        │
        └─► passed into the container
                    │
                    ▼
          Qt selects the X11 display
                    │
                    ▼
       /tmp/.X11-unix socket mount
                    │
                    ▼
       X11/XWayland access control
          authorized by xhost
                    │
                    ▼
      Window displayed on the desktop
```

On the tested system, the complete path is:

```text
PySide6 application
        ↓
X11 Qt platform integration
        ↓
mounted /tmp/.X11-unix socket
        ↓
XWayland
        ↓
GNOME running under Wayland
        ↓
screen
```

## Summary

The essential display configuration consists of:

```yaml
environment:
  - DISPLAY=${DISPLAY}
  - QT_X11_NO_MITSHM=1

volumes:
  - /tmp/.X11-unix:/tmp/.X11-unix:rw
```

together with the temporary X server authorization applied by the host script:

```bash
xhost +local:docker
```

These elements allow the Qt application running inside the container to display its window on the Linux host desktop.

The `network_mode: host` setting makes the container share the host’s network stack, but it is not required for the local X11 connection when that connection uses the mounted `/tmp/.X11-unix` socket.

The application is therefore containerized with its Python, PySide6, and system dependencies, while its graphical display remains deliberately connected to the host through X11 or XWayland.
